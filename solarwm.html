SolarWM：全开放的长时程视频世界模型基础栈

用可重配置的多源数据引擎把 10 个异构数据集折成 142.6 万条统一契约的片段（约 25.85 TB / 29,272 个分片），再用backbone-native 适配框架在同一套相机条件 / 训练 / 推理接口下实例化 4 个 5B–33B 模型（Wan2.2、LTX-2.5、MiniMax-H3），最后用三阶段配方把双向视频生成器变成少步因果模型——只用 5 秒片段训练，却能做分钟到小时级的实时交互 rollout。

①

一句话与三根支柱

论文的定位不是「又一个更强的视频生成模型」，而是「让世界模型研究可复现、可比较、可扩展的基础设施」。

一句话

SolarWM 把三件互相纠缠的事拆开做：数据契约与 mixture 构造解耦，backbone 原生表示与 统一接口解耦，双向适应与 因果化蒸馏解耦。然后把数据、流水线、配方、权重、框架全部开源。

① 开放、可重配置的数据基础设施

1,425,694 条 canonical clips，来自 10 个源数据集、组织成 14 个可独立寻址的 owner。统一成 frame-aligned 契约：观测、metric 相机几何、caption、质量元数据、选择决策、provenance 六类信息齐备。

② backbone-native 的可扩展模型家族

一套框架支撑 4 个 5B–33B 模型（Wan2.2-5B/14B、LTX-2.5-22B、MiniMax-H3-33B），保留每个 backbone 的原生表示与目标函数，而不是把它们改造成同一种结构。

③ 统一的三阶段训练配方

Bidirectional adaptation → Teacher-Forced AnyFlow 初始化 → DMD via Self-Gradient Forcing。跨异构 backbone 共用同一条路线，不需要额外的 ODE 初始化或一致性蒸馏初始化。

它想解决什么痛点

层面异构性体现在哪朴素做法的后果
数据侧各源在 temporal scale、camera 约定与 metric scale、视觉质量、motion 分布、caption 风格上都不同朴素混合 → 监督不一致：单源上表现好的模型，多源混合训练后反而退化
模型侧不同视频生成器的 latent 表示、attention 结构、conditioning 机制各不相同要么牺牲预训练能力做统一改造，要么写 backbone-specific 实现 → 无法系统比较、无法复现
长时程侧自回归 rollout 的误差累积、KV cache、运动漂移常见对策是长序列微调或 attention sink；而前提是要能有小时级的稳定 rollout

论文 Table 1 做了一张「代表性交互式世界模型发布矩阵」，对比各家是否放出 weights / 推理代码 / 训练代码 / 数据 / 完整记录 / 数据处理流水线 / 精确配方 / 多 backbone——SolarWM 的卖点正是这一行的「全 ✓」。

1) 统一样本契约

每个样本表示为 S_i = (V_i, P_i, K_i, C_i, m_i, q_i, π_i)：

V：视频帧 P ∈ ℝ^(N×4×4)：metric camera-to-world K ∈ ℝ^(N×4)：逐帧内参 (fx, fy, cx, cy) C：dense caption m：来源/媒体元数据 q：完整 metric 记录 π：provenance / lineage

关键设计是三个命名空间分离，同一份物理数据可被不同配方复用而不复制：

physical corpus样本本体 + 全部标注
→
logical recipesplit、tier policy、source 权重、repeat factor
→
model viewbackbone 专属时间窗或预计算 latent

落到代码里，这套契约是「纯数据契约、零代码耦合」：主仓库与数据引擎子模块之间没有任何 import，只靠三样东西对接——WebDataset member 布局、index schema、以及 latent 侧的 encoder_contract.json 指纹（契约摘要会写进 index 行的 encoder_contract_digest）。

# WebDataset 每个样本的必需 member（数据引擎侧定义） REQUIRED = ("intrinsics.npy", "meta.json", "poses.npy", "prompt.txt", "video.mp4") optional = gt_depth.npz | action.npy | audio.m4a # 时间规格（spec.py）：5s→121f, 60s→1437f, 81f, 160f, 960f

2) Metric-scale 相机标注（全篇最工程的一段）

目标是让不同来源的相机轨迹进入同一个 metric 尺度。按源可用几何分路处理：

源的几何条件处理路径
纯视频（无位姿）Pi3X 给时序一致但尺度模糊的结构 → MoGe-2 给逐帧 metric-depth anchor → 两者 depth 对齐融合 → 送进改造版 VIPE SLAM backend：估 6-DoF 轨迹，并用逐帧可独立优化的 (fx, fy, cx, cy) 做 bundle adjustment；初值来自 GeoCalib（对 zoom / focal-length 漂移是必需的）
有 GT / COLMAP 位姿保留原轨迹，只用 Pi3X 把预测结构与轨迹连到 metric gauge：用 robust Umeyama Sim(3) 对齐相机中心，并用残差最低的 80% 帧重新估计
有 metric depth 无轨迹同样支持（论文给出该模式）

几条容易忽略但很关键的原则

  • 不做 corpus-wide 归一化：translation 保持 metric 单位，避免抹掉真实尺度差异。
  • 质量门 fail-closed：检查几何有限性、正焦距、合理 FOV、焦距一致性 |fx−fy| / (½(fx+fy)+ε)、时序尺度稳定度 std(s)/mean(s)；证据不足直接卡掉，而不是猜。
  • 相机数组的权威格式是 c2w；logd4 只是「首帧 rebase 之后」的模型侧变换，绝不改写存储张量。

3) LTX Clean Plate：把「人 / 车」这类不可控动态去掉

动态人车既不能用相机解释、又不适合作为可交互内容，于是用 LTX-2.3 Clean Plate IC-LoRA（8 步去噪、strength 1.0）派生 3 组新 owner。输入 1248×704，输出 1280×720 @ 16 fps。规模：

SpatialVID-Clean 298,514 MiraData-Clean 135,224 Sekai-Walking-Clean 109,248 合计 543k clean clips

重要细节：clean 输出不继承源 clip 的质量——caption、视觉指标、语义指标、相机诊断全部重算；metric scale 由确定性源帧对应关系恢复，有歧义就 fail closed。

4) 全量 caption：Kimi-K2.6

全部 1.43M clips 走同一条 Kimi-K2.6 production pipeline（输入 1 fps、最多 64 帧、最长边 768 px、JPEG qscale 3、无音频；温度 0、seed 0、不做 thinking），输出严格 JSON、恰好 6 个顶层字段：

为什么要把「相机运动 / 镜头术语」从 caption 里硬性剔除？——防止文本条件泄露相机控制，让相机只能从几何条件进来，控制链路才干净。最终只有 dense_caption 会被当作 text condition 使用。

5) 质量 / 运动指标 → 三档分层

每个 dataset owner 冻结一份带版本的 policy，把 clip 分成三个互斥标签：xhigh（kept 规则 + 更严的 promotion 规则）、high（只满足 kept 规则）、rejected（连失败原因一起保留）。

camera 完整性（FOV / 焦距散度 / scale CV） 饱和度统计 DOVER technical + aesthetic 均值 FFmpeg VMAF Motion UniMatch / GMFlow 稠密对应强度 PySceneDetect 切点数 + Kimi transition Kimi quality / entity density / scene type / flags

policy 有意做得非对称（每个 owner 阈值不同），避免把每个算出来的指标都变成 gate。几个例子：DL3DV-10s/60s 要求 FOV ∈ [25,120]°、焦距散度 ≤ 0.20、scale CV ≤ 2、Kimi 质量 ≥ 4、DOVER ≥ 0.20；Sekai-Game 反而不设通用相机几何与饱和度 gate（为了保住高运动样本），只要求 UniMatch ≤ 350、DOVER ≥ 0.20；SpatialVID 要求零切点、DOVER ≥ 0.35。未使用的指标也全部入档，方便以后换策略重筛。

论文写「10 个源数据集」，仓库 README 写「14 个数据集」，两者并不矛盾：DL3DV 被拆成 DL3DV-10s / DL3DV-60s 两个 temporal view，另外从 MiraData、Sekai-Walking、SpatialVID 派生了 3 个 Clean Plate owner，合起来就是 14 个可独立过滤 / 加权 / 选择的 owner。

③

模型家族：一套接口，四种原生 backbone

论文第 6 节。核心是「不改造 backbone，只加相机条件」。

统一相机条件化：Fused-PRoPE

把每条相机轨迹转成与视频帧对齐的几何条件（poses + intrinsics + frame alignment + normalization transform），再用 fused-PRoPE 注入：backbone 先用原生 video RoPE 表达 video token 的时空位置 → 相机 poses/intrinsics 决定一组 projective rotations，直接施加在 Q、K、V 三个张量上 → 只做一次 self-attention → 输出前施加匹配的输出变换 → 回到原生 output projection。
也就是说：相机运动由 attention 计算本身引入，不追加额外 condition token、不建独立 camera branch、不多跑一遍 attention。

四个模型保留了各自的什么

模型保留的原生组件图像条件音频VAE 降采样 (T/S)
SolarWM-wan2.2-5B Wan2.2 TI2V-5B 原生 latent 路径（48 通道 VAE latent），无独立 y 分支 无额外条件：首个 latent 作 clean image anchor 并排除出 video loss；其余 latent 作 video target 去噪 无4× / 16×
SolarWM-wan2.2-14B 取 Wan2.2 I2V-A14B 的 high-noise expert 初始化，当作覆盖全 timestep 的单一 dense 模型；弃用双 expert 路由与噪声边界 官方 y：4 通道首帧 mask + 16 通道图像 latent，与 noisy 16 通道 target 拼接；首个 target latent 仍为 noisy 且被监督 无4× / 8×

SolarWM-minimax-h3-33B 33B Omni Transformer，保留 multimodal packing（Qwen caption/image rows + 1 帧 VisualVAE anchor + audio rows + target-video rows） Qwen rows + VisualVAE 首图 anchor 保留 audio rows（小），填官方 AudioVAE 的静音编码并置 zero audio loss (17n+5)→(5n+2) / 16×

三个值得注意的实现细节

  • LTX 路线：相机条件只插进 video self-attention，Qwen conditioner / VisualVAE / AudioVAE 全部冻结——把「加控制」的影响面压到最小。
  • MiniMax-H3 路线：相机注入保留预训练 head split——camera_prope_head_dim_start: 96 / end: 128，即维度 [0:96) 保持原生内容表示与 MM-RoPE，只有 [96:128) 在 VisualVAE anchor 与 target-video rows 上接受 camera-relative-pose PRoPE。相当于给相机单独留了一段专用维度。
  • 代码里有三份独立的 PRoPE 实现：Wan 侧是 vendored 自 PRoPE 项目（camera_prope.py，NOTICE 标注 Apache-2.0/MIT 双许可）、LTX 侧 torch_prope.py + camera.py、H3 侧 torch_prope.py（logd4_relative_viewmats）+ camera.py。说明这个「窄口子」实际是各 backbone 分别打磨的。
④

三阶段配方：从双向生成器到实时因果世界模型

论文第 4 节。命名有两套：论文正文写 Stage 1/2/3，仓库与 README 写 Stage0.5 / Stage1 / Stage2，是同一件事。

Stage0.5 · Bidirectional Adaptation全窗口双向 attention，学 camera-conditioned 世界数据
→
Stage1 · Teacher-Forced AnyFlowclean history 条件化 noisy target chunk，学到 few-step 流映射
→
Stage2 · DMD via SGF冻结 teacher + 可训练 fake 模型，在 student 自己的 AR rollout 上做分布匹配

Stage0.5 —— 双向适配

把预训练视频生成器适配到 camera-conditioned 世界数据，整个训练窗口保持双向 attention，目标函数仍是 backbone 原生的 flow / velocity 匹配：

双向适配损失（论文 Eq. 1） Lbid = 𝔼z₀, t, ε [ ‖ fθ(zt, t, c) − ut ‖₂² ]

其中 c 汇集 text / image / camera 条件，ut 是该 backbone 的原生 flow 或 velocity target。这个 checkpoint 一举两用：既是因果训练的初始化，又是 Stage2 里 DMD 的 frozen 双向 reference（teacher）。

Stage1 —— Teacher-Forced AnyFlow 初始化

把 latent 序列切成有序 block；预测当前 block 时，模型只能看到当前的 noisy state 与干净的 ground-truth history，未来 block 被 mask 掉。训练时采样一对噪声水平 (t, r)：

Teacher-Forced AnyFlow 损失（论文 Eq. 2） LTF-AF = 𝔼 [ Σk ℓAF( fφ ; zkt, t, r, z<k0, c ) ]

ℓAF 监督的是任意两档噪声水平之间的流映射，所以一步就得到 few-step 自回归生成器。机制上：

  • clean history 提供稳定条件：teacher forcing 消掉早期误差累积；
  • AnyFlow 把模型直接暴露给 few-step 采样实际使用的有限噪声跳变，而不是只学无穷小步长。
关键收益：因为 AR initializer 从一开始就是 few-step 的，省掉了 Causal Forcing 的 causal ODE 初始化、以及 Causal Forcing++ 的 causal consistency distillation 初始化这两个独立阶段。而且这个阶段只做「短的因果适配」，不是重新学外观与运动，所以收敛很快。

Stage2 —— DMD + Self-Gradient Forcing

因果 student 按与推理完全相同的时间规则在自己的 rollout 上生成轨迹；用 detached rollout-and-replay（Self Gradient Forcing）让梯度能穿过 KV cache 回传。三个角色分工：

frozen 双向 teacher估计 real 分布
+
可训练 fake 模型跟踪 student 不断演化的 rollout 分布，只在生成样本上优化
→
分布匹配方向两者之差给出 DMD 梯度
DMD 梯度（论文 Eq. 3） ∇ψ LDMD = 𝔼 [ JGψ⊤ · w(t) · ( sfake(zt, t, c) − sreal(zt, t, c) ) ]

J 把匹配信号映回 generator 参数，w(t) 控制不同噪声水平上的权重尺度。teacher 固定、fake 跟随的分开优化，既保住稳定的质量参照，又让训练信号跟踪变化的 student 分布。

哪些路线是合法的？

config/routes.py 用一个 _SUPPORTED 冻结集合硬编码了 9 条合法路由，非法组合在分配 GPU 之前就会被拒绝：Wan2.2-5B 四条（stage0p5 / stage1-tf-fm / stage1-tf-anyflow-v1_5 / stage2-sgf）、MiniMax-H3 三条、Wan2.2-14B 仅 stage0p5、LTX-2.5 仅 stage0p5(native_rectified_flow)。

双向预训练（7.2） 4 条 backbone 在同一 OOD 协议下评测；首帧由 GPT Image 2 或 Krea 合成，固定 caption 与相机轨迹，覆盖 translation / rotation / mixed 6-DoF 共享的数据与相机契约可跨异构生成器一致迁移，同时保住各自的视觉先验
In-domain 验证（7.3.1） 样本取自 held-out validation pool（同源同流水线，不参与优化）：10 s 第三人称 rollout；以及不间断的 minute-scale rollout，覆盖 real-world / synthetic / game 主体外观与空间关系稳定，相机跟随正确，长时间 rollout 视觉连贯
OOD 初始化（7.3.2） 首帧全部来自 GPT Image 2 / Krea 合成，prompt 刻意覆盖语料罕见条件：风格化插画、超现实几何、非常规材质、戏剧性光照；每张图配多条轨迹（前向 / 侧移 / 转向 / 环绕 / 平移+旋转组合） 把「外观鲁棒性」与「控制响应性」两个因素分离开来考察
长视频生成（7.3.3） 不重启首帧、不注入 reference frame、不拼接短片段、不用 attention sink。minute-scale：合成首帧 + 复合轨迹，连续导航 5 个视觉上不同的场景；hour-scale：真实首帧，单次不中断 AR session 跑到 60 分钟端点 训练只用 5 s 序列，评测无需长序列微调；60 分钟端点仍可辨识且视觉连贯

论文自己总结的三条 finding（写在 Introduction 里，替代了 ablation 表）

① 不需要额外初始化阶段

不靠专门的 ODE 初始化或一致性蒸馏初始化，也能达到 SOTA。（仓库的 9 条合法路由也印证：从 Stage0.5 直接进 AnyFlow。）

② 优化量主要花在双向阶段

因果适配收敛很快，DMD 所需步数更少——配置里 Stage2 只有 4,000 步，而 Stage0.5/1 各 30,000 步。

③ 5 秒训练即可开放长时程

只用 5 s 序列训练，就能支持分钟–小时级 open-ended rollout，无需长序列微调或 attention sink。

局限：论文 Conclusion 没有 limitation 段落，也没有失败案例或定量误差。仅能从若干工程性保守设计中间接看出作者的谨慎：相机证据缺失时 fail closed、clean plate 不继承源质量、scene transition 预测标记为 unverified。

架构铁律（来自 docs/architecture.md）

四大契约

config / data / backends / execution 四个契约面。core 永不 import 具体 backbone，backend 之间禁止互相 import；数据集读取器不得从类名或数据集名推断相机归一化。这套约束解释了为什么 add-a-backbone 是「加一个目录」而不是「改框架」。

工程成熟度（明显高于同类研究仓库）

CI 不只是跑单测

ci.yml（job cpu-contracts）在 Py3.10/3.11/3.12 矩阵下跑 ruff + pytest，然后遍历全部示例配置逐个 config resolve 断言可解析，最后构建 wheel/sdist 并断言产物内容与可安装性。

可复现性被当作 public API

CONTRIBUTING.md 要求：改动样本顺序、相机约定、张量 shape/dtype、目标函数数学、checkpoint schema 或 validation 生成，必须附带聚焦的契约测试；新 stage 要有 config/data/objective/checkpoint/inference/validation/runtime 七类测试才能注册为 supported route。

测试与代码 1:1 镜像

71 个测试文件、584 个测试函数，布局镜像 src/。分布偏重 backbone（wan22 19 文件/222 测试）与 data contract，通用 training/inference 引擎测试相对薄。

还有个少见的细节：给 AI agent 的说明书

几点观察与评述

以下是基于论文与代码通读的判断，不是论文原文结论。

值得肯定的地方

  • 把「可复现性」当作一等公民来做。多数世界模型论文只放权重与 demo，SolarWM 放的是「processed corpus + 选择记录 + 精确 recipe + 多 backbone 框架」。数据契约专门为 provenance 留字段、rejected 样本连失败原因都保留、Tier 策略带版本冻结——这些都是为了让别人能重跑出同样的 mixture。
  • 论文缺的超参，仓库补齐了。论文没给学习率、步数、batch size、并行度，但配置文件把三阶段的全部超参都摆了出来（甚至包括 Stage2 的 4,000 步 vs 前两阶段各 30,000 步这种最能说明问题的对比）。对想复现的人来说，配置的可读性比论文正文更重要，这一点他们做对了。
  • 「backbone-native」是比「统一改造」更聪明的路线。保留 Wan2.2 的 latent 路径、LTX 的 rectified-flow 约定、H3 的 multimodal packing 与 head split，只把相机控制从一个精心设计的窄口子（fused-PRoPE）注入。预训练能力不掉，又能横向比较四个模型。
  • 工程纪律罕见地强。core 不 import backbone、backend 互不 import、CI 逐个 resolve 所有配置并校验打包产物、把可复现性契约写进 CONTRIBUTING 作为 public API、非法 stage 组合在分配 GPU 前就被拒绝——这套东西在学术仓库里属于上乘。
  • 数据的工程细节经得起看。相机标注分三路处理、metric 尺度不强归一、clean plate 不继承源质量、caption 硬性剔除相机术语——每一条都能看出是对「什么会让控制信号变脏」有过真实踩坑。

需要保留怀疑的地方

  • 实验部分没有数字。没有 FVD / 相机误差 / 用户研究，也没有消融与训练成本。既然论文主张「同一框架支撑四个 backbone 并可系统比较」，那么一张跨 backbone 的定量对比表恰恰是最该有的东西。目前只能靠质化图与「受控协议」支撑结论。
  • 「实时交互」缺量化。16 fps / 4 步是生成规格，但没有端到端延迟、吞吐、显存占用——而这些恰恰是「交互」的真正门槛。（4 步 + 16 fps 的组合也意味着必须靠 KV cache 与流水线并行把延迟压下去，但论文没有给出这条链路的数字。）
  • 小时级 rollout 的稳定性证据是「单个 60 分钟样例」，没有多案例统计，也没有漂移度量。对世界模型而言，长时程漂移的分布往往比最好样例更重要。
  • 开放度有三层门槛。代码 Apache-2.0 很干净，但权重全部 gated、完整 raw-WDS 要走表单申请、13 个 latent generation 只发布了 2 个。宣称的「fully open」在落地时要打折看。
  • 许可证是真陷阱。LTX-2.x 与 MiniMax H3 的社区许可（后者含地域限制）独立于仓库的 Apache-2.0，商用前必须逐个核对。
  • 规模数字要自己核对口径。「10 datasets」与「14 datasets」的差异源于 owner 划分，不看第 5 节细节容易误引。

对做推理与部署的人意味着什么

这一条对你在做的工作（MiniMax-H3 / Wan2.2 在 vLLM-Omni 与昇腾 NPU 上的部署）特别直接：

  • 它把 MiniMax-H3 与 Wan2.2 变成了「因果化 + 相机可控」的形态，而且是 4 步、16 fps 的少步模型。少步意味着单位时间去噪计算量大幅下降，正好是推理侧最关心的指标。
  • 长时程 rollout 靠的是 KV cache 复用与自回归状态维护——Stage2 的 SGF 明确处理「梯度穿过 KV cache」，代码里还有 H3RawKVCache 与专门的 SGF attention。这与推理引擎里的 cache 管理、连续批处理、状态复用完全是同一套工程关注点。
  • 三套独立环境是明确的部署信号：三个 backbone 的 torch / CUDA / diffusers 版本互相冲突。若要在同一集群同时支持多条 backbone，容器化(多镜像)几乎是必需的——他们没给 Dockerfile，这一步得自己做。
  • 权重是 gated 的，需要先接受 H3 仓库的访问条款；数据集还要走表单。想复现的团队要预留这一步时间。
一句话总结：SolarWM 的贡献重心不在「刷新某个 benchmark」，而在把长时程视频世界模型这条链路（数据 → 相机控制 → 因果化 → 实时推理）完整地开源并标准化。论文的实验部分偏弱，但仓库的配置、契约与 CI 补足了很多论文没说的事。如果你想在自己的 backbone 上复现「双向 → 少步因果 → 长时程交互」这条路线，这目前是最完整的公开参考实现。
