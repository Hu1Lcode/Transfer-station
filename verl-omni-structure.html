模块逐个看

每个子包的职责、关键文件、以及它在架构里的角色。

1) trainer/ —— 编排层

文件作用
main_diffusion.py (378 行)扩散 RL 主入口。@hydra.main(config_path="./config", config_name="diffusion_trainer")，解析配置后按 _get_trainer_cls(config) 选出 trainer 类并跑 run_diffusion()；内置 nsight profiling 支持
main_diffusion_v1.pyV1 架构入口（TransferQueue 流水线，支持 sync 与 separate-async）

diffusion/ray_diffusion_trainer.py编排核心：BaseRayDiffusionTrainer(ABC) → PolicyGradientRayTrainer（GRPO/DPPO 系）与 DirectPreferenceRayTrainer（DPO 系）；负责 init_workers()、fit()、dataloader 构造，并把 agent loop worker 注册成 Ray actor
diffusion/diffusion_algos.py算法扩展点：loss 注册表 + 优势估计注册表（详见下一节）

2) workers/ —— 执行层

这一层回答「用什么算」：训练后端 × rollout 引擎，各自独立可换。

engine/fsdp/diffusers_impl.py（扩散）与 omni_impl.py（全模态）——基于 FSDP 的默认训练后端
+
engine/veomni/diffusion_impl.py——把 VeOmni 当作训练后端接进来（对应 64 卡配方）
+
rollout/vllm_rollout/vLLMOmniHttpServer / vLLMOmniReplica 继承 verl 原有 server/replica；diffusion_strategy 与 ar_strategy 分别处理扩散与自回归生成；zmq_utils 做进程间通信，npu_utils 做 NPU 适配

workers/config/ 下按 diffusion/ 与 omni/ 分目录存放 worker 侧配置；checkpoint_engine.py、engine_workers.py、omni_engine_workers.py 负责 checkpoint 与 worker 生命周期。

3) pipelines/ —— 模型适配层（最大的一块，18k 行）

这里是「新增一个模型」的唯一落点。抽象基类集中在 model_base.py：

DiffusionModelBase(ABC) DiffusionI2IModelBase OmniModelBase(ABC) VllmOmniPipelineBase OmniRolloutPipelineBase NonDiffusersModelBase

每个模型目录的「三件套」模式

# 绝大多数扩散模型目录的结构（以 qwen_image_flow_grpo 为例） pipelines/<model>/ ├── common.py # 模型常量、prompt 模板、共享工具 ├── diffusers_training_adapter.py # ★ 训练侧：如何构造 diffusers 模型、前向、算 loss ├── vllm_omni_rollout_adapter.py # ★ 推理侧：如何调 vLLM-Omni 生成、取 latent / logP └── agent_loop.py # 可选：多步 / agent 化 rollout（ltx2、minimax_h3 有）

4) reward_loop/ + utils/reward_score/ —— 奖励层

奖励被拆成「怎么调度」与「怎么打分」两块：

  • reward_loop/reward_loop.py —— 奖励循环主逻辑；local_accelerator_reward_loop.py —— 用本机加速器（与训练同机）算奖励。
  • reward_loop/reward_manager/ —— 按模态分文件：visual.py、audio.py、multi.py（多奖励加权）。
  • utils/reward_score/ —— 15 个奖励实现，覆盖偏好模型与任务奖励：
hpsv2_reward hpsv3_reward pickscore_reward unified_reward genrm_ocr mmk12_reward choice_reward clap imagebind jpeg_compressibility http_scorer_client latent_http_scorer_client audio_http_scorer_client

注意三个 http_scorer_client：奖励可以不在训练进程里算，而是通过 HTTP 打到独立的 scorer 服务——这正是「异步奖励 + latent 直接打分（省掉 VAE 解码）」的实现路径。

5) agent_loop/ —— 多步 / agent 化 rollout

把一次生成包装成可多轮的循环：diffusion_agent_loop.py（基础）、diffusion_agent_loop_tq.py（TransferQueue 版）、composite_agent_loop.py（组合多个 loop）、single_turn_agent_loop.py（单轮兜底）。模型侧可以在自己的 pipeline 里放 agent_loop.py 覆写默认行为。

两套扩展机制

这个项目之所以能撑起「17 模型 × 11 trainer」的组合，靠的是注册表 + 适配器两个模式。

A. 算法侧：装饰器注册表

trainer/diffusion/diffusion_algos.py 提供两个注册入口，新算法不用改任何 if-else：

@register_diffusion_loss("flow_grpo") # 注册一个 loss class FlowGRPOLoss(DiffusionLossFn): ... @register_diffusion_adv_est("grpo") # 注册一个优势估计器 def compute_flow_grpo_outcome_advantage(...): ... # 运行时按名字取用 get_diffusion_loss_fn(name) / get_diffusion_adv_estimator_fn(name)

仓库里已内置的 loss 实现

FlowGRPOLoss FlowDPPOLoss GRPOGuardLoss DPOLoss DiffusionNFTLoss KLLoss DistillKLLoss DistillFlowMatchingMSELoss

优势估计的关键实现细节

compute_flow_grpo_outcome_advantage() 就是 GRPO 的组相对优势，被搬到了扩散场景：按 prompt 的 index 分组，组内对 outcome 奖励做归一化。它暴露了两个容易忽略的开关：

norm_adv_by_std_in_grpo=True # True：除以组内 std（原始 GRPO） # False：不除 std（Dr.GRPO 的做法） global_std=True # 用全局 std 还是组内 std 做归一化

也就是说，「GRPO / Dr.GRPO / 各种 std 变体」在这里只是配置开关，不用改代码。

B. 模型侧：适配器三件套

接入一个新模型 = 在新目录下实现训练适配器与 rollout 适配器两个类，分别对应「用什么算 loss」和「怎么生成」。数据在两侧之间用统一抽象传递：

MediaInput PromptBundle OmniRolloutRequest MediaSpec DiffusionIOSpec DiffusionRolloutOutput RequestBatch

这套抽象的意义在于：同一个 trainer 可以驱动扩散、自回归、全模态三类完全不同的生成过程，因为差异被关在了适配器内部。

读完代码后的三个判断

1. 分层非常干净：编排（trainer）/ 执行（workers）/ 适配（pipelines）/ 奖励（reward_loop）四层几乎没有反向依赖，所以换后端、加模型、加算法都是「填空」而不是「改框架」。
2. 扩张策略是「一份模型一份配方」：68 个 example 脚本 + 17 个 pipeline 目录，宁可重复也不抽象成难以调试的通用层——这是工程上务实的选择。
3. NPU 是一等公民：A2/A3 专用 Dockerfile、14 个 _npu.sh 配方、npu_utils、npu_smoke 测试，说明昇腾支持是持续维护的路径而非一次性适配。
